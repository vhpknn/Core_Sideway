# RULES: กติกากลางของแม่แบบ New_Strategies

กติกาข้อ R-1 ถึง R-9 ใช้กับทุกกลยุทธ์ที่เริ่มจากแม่แบบนี้ มติ D-18, D-19, D-26 ถึง D-30 ที่คัดลอกมาใน `docs/decisions/` ยังมีผลตามเดิม ถ้าขัดกันให้ยึดมติ D ก่อน แล้วแจ้งผู้ใช้

## R-1 Core
- ไฟล์ใน `Core/v<รุ่น>/` และ `Strategies/<ชื่อ>/v<รุ่น>/Core/` เป็นสำเนา ห้ามแก้ (มติ D-06) `verify_core` จะจับถ้าแก้
- กลยุทธ์ต้องการความสามารถที่ Core ไม่มี: หยุด แจ้งผู้ใช้ และเปิดเป็นงาน Core ที่ Repo EA_Platform_Core แล้วค่อยนำ Core ใหม่เข้าด้วย `tools/update_core.py`
- โฟลเดอร์กลยุทธ์ `Strategies/<ชื่อ>/v<X>/` ใช้ Core รุ่น `Core/v<X>/` เลขเดียวกันเสมอ (มติ D-28.1)

## R-2 หนึ่ง Repo หนึ่งกลยุทธ์
AI เห็นเฉพาะ Repo นี้ ห้ามอ้างโค้ดกลยุทธ์อื่นนอกจากตัวอย่างใน `reference/Hedge_example/` (อ่านเป็นตัวอย่างรูปแบบเท่านั้น)

## R-3 TAG, ลำดับ EA และ Magic (ไม่มีทะเบียนกลาง)
- ผู้ใช้กำหนด TAG 3 ตัวอักษร (A ถึง Z) และลำดับ EA ตอนรัน `tools/init_strategy.py` Magic ฐาน = ลำดับ x 10000 Magic ของแต่ละชุดค่าอยู่ในช่วงฐาน ถึง ฐาน+9999 (ตรงกับ `Core_Identity` และ `verify_core`)
- `init_strategy` สแกนโฟลเดอร์ข้างเคียงและเตือนถ้า TAG หรือลำดับ/Magic ฐานซ้ำกับกลยุทธ์อื่น ถ้าสแกนไม่ครอบคลุม (เช่น Repo อยู่คนละที่) ผู้ใช้ต้องตรวจเอง
- Magic ที่ใช้แล้วห้ามนำกลับมาใช้ และสอง EA ที่ Magic เดียวกันบน Symbol เดียวกันในบัญชีเดียว ตะกร้าจะปนกัน
- ค่าตั้งต้นเก็บใน `STRATEGY_IDENTITY.txt` และ `#define` ในไฟล์ `<ชื่อ>_EA.mq5`

## R-4 เลขรุ่นและ tag
- โฟลเดอร์รุ่นใหม่เกิดเมื่อ Core เปลี่ยนรุ่นเท่านั้น (R-1) สร้างด้วย `tools/update_core.py` รุ่นเก่าแช่แข็ง
- แก้เฉพาะกลยุทธ์โดย Core ไม่เปลี่ยน: แก้ในโฟลเดอร์รุ่นเดิม ไม่แก้ `Strategy_Version()` และติด tag `<ชื่อ>-v<รุ่น>-r<N>` (เช่น `smc-v1.0.1-r1`) N เริ่มที่ 1 ต่อรุ่น ส่วน `-r0` ใช้ติดฐานของโฟลเดอร์รุ่นใหม่เมื่อทดสอบผ่านครั้งแรก
- Commit เอกสารปิดงานก่อน แล้วค่อยติด tag ที่ Commit นั้น

## R-5 วิธีทำงานกับ AI
1. ปรึกษา: AI สรุปสเปกและถามเฉพาะจุดที่ขาด ห้ามเดาสเปก ผลสรุปลง `docs/BLUEPRINT.md`
2. วางแผน: AI ส่ง Folder Tree, หน้าที่ต่อไฟล์, ผลกระทบ แล้วรอคำว่า "เริ่มงาน"
3. เขียนโค้ด: ไฟล์ใหม่ส่ง Full Code พร้อม path ไฟล์เดิมส่งเป็น Jigsaw Patch (FIND/REPLACE) ตามกติกาใน `docs/handoff/JIGSAW_PATCH_RULE.txt`
4. AI ไม่ Commit ไม่ push ไม่ติด tag ไม่สร้าง branch ผู้ใช้ทำเอง
5. ชื่อฟังก์ชันและ API ต้องมาจากไฟล์ที่เปิดอ่านจริง ไม่มีให้บอกว่าไม่มี

## R-6 การทดสอบ
- ทดสอบบนบัญชี Demo เท่านั้น ก่อนเทรดจริง บันทึกผลใน `docs/work/TEST_MATRIX.md` ระบุ Magic, ชุดค่า, เวลา, ผล, หลักฐาน
- สถานะผล: PASS (มี Log หรือภาพ), PASS* (ผู้ใช้รายงานข้อความ ไม่มีหลักฐานแนบ), BLOCKED, ยังไม่ทดสอบ (ความหมายอื่นดู D-19) คอมไพล์ผ่านไม่ใช่หลักฐานว่าไม่มีบั๊ก
- ค่าที่ใช้ทดสอบ (Magic ทดลอง, Timeout สั้น) ห้ามเก็บเป็นไฟล์ `.set` ใน Repo และลบ Global Variable ทดสอบ (F3) หลังจบ

## R-7 ก่อน Commit
รัน `tools\run_checks.bat` ต้องได้ sync_core ตรงกันหมด, verify_core ERROR 0, check_docs ERROR 0 แล้วบันทึกใน `docs/work/LOG.md` และอัปเดต `docs/work/CURRENT_STATE.md`

## R-8 อัปเดต Core (สรุป)
ใช้ `tools/update_core.py` (ดู `README_FIRST.md` เฟส 4) ความเสี่ยงขึ้นกับชนิดการเปลี่ยน: แก้บั๊กไม่เปลี่ยน API (ต่ำ), เพิ่ม API (ปานกลาง ต้องทดสอบส่วนที่เพิ่ม), เปลี่ยนหรือลบ API เดิม (สูง คอมไพล์ล้มและต้องแก้กลยุทธ์) รุ่นเก่าอยู่ครบ ย้อนกลับได้โดยใช้โฟลเดอร์เดิม

## R-9 มติของกลยุทธ์
มติเฉพาะกลยุทธ์นี้บันทึกใน `docs/decisions/STRATEGY_DECISIONS.md` เลข S-01, S-02, ... ห้ามใช้เลข D-NN ซึ่งเป็นของแพลตฟอร์ม
